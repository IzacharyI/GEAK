## What this is, and what it is not

An index of the same operator family written six ways, so that a FlyDSL author can find how
somebody else answered a question before answering it from scratch. Every row points at
`file:line` in an AITER checkout at a named commit.

It contains **no performance claims and no rankings.** Nothing here says a tile is good, or
that one language beats another. That is deliberate and it is the reason the page can be
generated: a decision that was made is a fact readable from source, while a decision that was
*right* is a measurement, and measurements live in `expert_skills/` attached to the run that
produced them. Mixing the two is how a corpus becomes folklore.

Read a count as **"this many places state this decision in source"** — never as
"this language does this and the others do not." A compiler-chosen decision is still a
decision; it is simply not in the text. See the coverage note below.

The zeros are the interesting part, and they are easy to misread. `scheduling` is dense in
FlyDSL and empty elsewhere, but Triton kernels are scheduled too — by a compiler pass, and CK
by a `BlockGemmPipelineScheduler` enum, neither of which is a per-instruction statement a grep
can find. Likewise `tile_shape` is nearly empty for Triton not because Triton kernels have no
tiles, but because their tiles arrive as `tl.constexpr` arguments whose values are in the
shipped JSON (see the tunable-surface and tuned-starting-point sections).

So: a filled cell means *the decision is written here, at these lines*. An empty cell means
*not stated in source in a form this extractor recognises* — which may mean the decision is
delegated, encoded in a name, or simply that no rule exists for that idiom yet. The rules are
listed in `_extract_impl_facts.py`; a missing idiom is a fixable gap, not a finding.

lines that state them. Values are verbatim; where a rule captured a sub-expression, that is
what is shown.


Values marked `[gfx…]` sit inside an architecture-conditional branch. That is a hint about
where to look, not a filter: the same number outside a branch may still be arch-dependent in
practice, and a number inside one is not necessarily wrong elsewhere.

## Shipped tuned starting points

per-shape JSON, one file per `gfx`-and-variant, each mapping an M bucket to the knobs that won
on the box that ran the sweep. That makes this the most valuable table here for anyone starting
a kernel: a configuration that is known to compile and known to have been measured beats a
guessed tile, even when it is not optimal for the shape at hand.

never have tried otherwise. Knobs that moved with the shape are listed as varying, with the
value counts, because *which knobs matter* is itself the useful signal. Exact per-shape rows are
not reproduced; open the JSON named in the group for those.
